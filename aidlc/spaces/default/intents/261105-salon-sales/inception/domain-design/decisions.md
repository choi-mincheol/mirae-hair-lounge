## ADR-001: 기능 묶음은 auth, product, client, sale, report, common 여섯 개

### Status
Accepted

### Context
작업 방식(Practices Discovery Q8)에서 패키지를 `product`, `sale`, `report`, `auth`, `common`으로 나누기로 했습니다. 그 뒤 요구사항과 화면 설계에서 입고·재고(FR3), 거래처(FR4), 할부·입금(FR7), 직원 요청 승인(FR6.3, FR6.4)이 더해졌습니다. 각 묶음은 자기 테이블을 혼자 고쳐야 하므로, 새 기능을 어느 묶음에 둘지 정해야 했습니다. 1인 프로젝트이고 한 프로세스로 실행합니다.

### Decision
Q1 B를 택합니다. `auth`(로그인·계정), `product`(분류·상품·옵션·입고·재고), `client`(거래처), `sale`(판매·품목·변경 이력·할부·입금·요청), `report`(실적·대시보드), `common`(공통) 여섯 개로 나눕니다. 각 패키지 안은 작업 방식대로 controller/service/mapper로 나눕니다. 처음 정한 네 기능 패키지에 `client` 하나가 더해집니다.

### Consequences
- 좋은 점: 재고 숫자를 고치는 코드가 `product` 한 곳에만 있어 음수 재고를 막는 규칙이 흩어지지 않습니다. 판매 금액·회차·입금·요청 규칙이 `sale` 한 곳에 있어 승인 때 다시 계산하는 규칙(화면 설계 R-06)을 한 트랜잭션 안에서 처리합니다.
- 나쁜 점: `sale`이 가장 큰 패키지가 됩니다(엔티티 5개). 커지면 패키지 안에서 `sale.installment`, `sale.request`처럼 하위 패키지로 나눕니다.
- 그 밖: 작업 방식의 패키지 목록에 `client`가 더해집니다. 이것은 작업 방식을 바꾸는 것이 아니라 같은 규칙(기능별 패키지)을 새 기능에 적용한 것입니다.
- 보안 영향: 권한 규칙은 `common`이 모든 패키지에 같은 방식으로 적용하므로, 패키지 수와 관계없이 권한 검사 위치가 한 곳입니다.

### Alternatives Rejected
- Q1 A, 잘게 나눔(`inventory`, `installment`, `approval` 따로): 장점은 패키지마다 책임이 작다는 것입니다. 하지만 할부 재분배, 입금이 있으면 취소 거부, 승인 시 재계산이 모두 판매 금액과 상태를 함께 바꾸므로 `sale`, `installment`, `approval`이 서로를 불러야 하고 순환 의존이 생기기 쉽습니다. 1인 프로젝트에 패키지 아홉 개는 많습니다.
- Q1 C, 처음 정한 네 개만(거래처를 `sale`에): 장점은 작업 방식 그대로라는 것입니다. 하지만 거래처는 판매와 생명 주기와 화면이 달라(먼저 등록, 거래 중지, 별도 목록·상세) 한 패키지에 섞으면 `sale`이 지나치게 커집니다.

## ADR-002: 의존은 한 방향, 거꾸로 필요한 두 곳은 포트로 뒤집기

### Status
Accepted

### Context
의존 방향을 Report → Sale → (Product, Client) → Auth → Common으로 두면 자연스럽습니다(판매가 상품과 거래처를 참조). 그런데 두 곳에서 거꾸로 필요합니다.
- 거래처 목록(S08)과 상세(S10)는 거래처별 미수금, 연체, 판매 내역, 할부 일정을 보여줘야 합니다(FR4.2, FR4.3). 이 데이터는 `sale`이 갖고 있습니다.
- `common`의 JWT 필터는 토큰을 검사할 때 계정이 사용 중지되었는지 확인해야 합니다(FR1.3). 계정은 `auth`가 갖고 있습니다.
그대로 부르면 Client ↔ Sale, Common ↔ Auth 순환이 생깁니다.

### Decision
두 곳 모두 부르는 쪽이 인터페이스(포트)를 정의하고, 데이터를 가진 쪽이 구현합니다.
- `client` 패키지에 `ClientSalesSummary` 인터페이스를 두고 `sale`이 구현합니다. 거래처 화면은 이 인터페이스만 부릅니다.
- `common` 패키지에 `UserAccountLookup` 인터페이스를 두고 `auth`가 구현합니다. JWT 필터는 이 인터페이스만 부릅니다.
Spring이 시작할 때 구현을 주입하므로 코드상의 의존은 한 방향입니다.

### Consequences
- 좋은 점: 의존 그래프에 순환이 없습니다. 미수금·연체 계산(FR7.4, FR7.5)이 `sale` 한 곳에만 있어 판매 목록, 거래처 목록, 대시보드가 같은 값을 보여줍니다.
- 나쁜 점: 인터페이스가 두 개 늘어 코드를 따라가기가 조금 어렵습니다. 테스트에서는 이 인터페이스를 가짜 구현으로 바꿔 끼울 수 있어 오히려 쉬워집니다.
- 보안 영향: 사용 중지된 계정의 토큰은 다음 요청에서 바로 거부됩니다. `UserAccountLookup`은 비밀번호 해시를 돌려주지 않고 사용 여부와 역할만 돌려줍니다.

### Alternatives Rejected
- Client 화면의 미수금을 Client 쿼리에서 판매 테이블을 직접 읽어 계산: 장점은 인터페이스가 없다는 것입니다. 하지만 연체 판단 규칙이 두 곳(sale, client)에 생겨 값이 어긋날 수 있습니다.
- 거래처 목록·상세 화면을 `report`로 옮김: 순환은 없어지지만 거래처 등록·수정 화면과 목록 화면이 다른 패키지로 갈라집니다.
- JWT 필터를 `auth`로 옮김: 작업 방식이 보안 공통 처리를 `common`에 두기로 했으므로 따르지 않았습니다.

## ADR-003: 쓰기는 소유 컴포넌트만, 읽기 전용 조회는 허용, 트랜잭션은 하나

### Status
Accepted

### Context
목록 화면은 다른 컴포넌트의 이름(등록자 이름, 상호, 상품명)을 함께 보여줍니다. 실적과 대시보드(FR8, FR9)는 판매·품목·상품·분류를 묶어 세야 하고, 판매 1만 건에서 2초 안에 열려야 합니다(NFR10). 판매 저장은 판매·품목·회차·이력과 재고를 함께 바꾸며 중간에 실패하면 아무것도 바뀌지 않아야 합니다(NFR5). 앱은 한 프로세스, 한 DB입니다.

### Decision
- 테이블에 쓰기(INSERT, UPDATE, DELETE)는 그 엔티티를 가진 컴포넌트의 mapper만 합니다. 다른 컴포넌트의 데이터를 바꿀 때는 그 컴포넌트의 service를 부릅니다(예: Sale → Product 재고 차감).
- 읽기 전용 조회는 다른 컴포넌트의 테이블과 JOIN해도 됩니다. 이름 표시용 JOIN과 `report`의 집계 쿼리가 여기에 해당합니다. 이런 읽기는 `components.md`의 depends_on에 "읽기 전용 조회"로 적습니다.
- 여러 컴포넌트를 거치는 쓰기는 가장 바깥 service 메서드(예: 판매 저장) 하나의 트랜잭션으로 묶습니다.
- SQL은 H2와 MariaDB에 모두 맞는 표준 문법만 씁니다(NFR9).

### Consequences
- 좋은 점: 실적 집계를 DB의 GROUP BY로 해서 NFR10을 맞추기 쉽습니다. 판매 저장이 한 트랜잭션이라 재고와 판매가 어긋나지 않습니다.
- 나쁜 점: 읽기 쿼리가 다른 컴포넌트의 테이블 구조에 기대므로, 테이블을 바꿀 때 `report`와 이름 JOIN 쿼리도 함께 고쳐야 합니다. 앱을 여러 서비스로 나누면 이 방식은 다시 정해야 합니다(지금은 나눌 계획이 없음).
- 보안 영향: 읽기 쿼리도 서비스 계층에서 권한을 검사합니다(실적은 관리자 전용). 직원 대시보드 쿼리는 매출 합계를 아예 조회하지 않습니다(FR9.2).

### Alternatives Rejected
- 모든 조회를 소유 컴포넌트의 service 호출로만 함: 경계는 깔끔하지만 실적처럼 여러 테이블을 묶는 집계를 애플리케이션에서 해야 해 느려지고 코드가 많아집니다.
- 실적용 별도 집계 테이블(읽기 모델)을 만들어 갱신: 1만 건 규모에는 과합니다.

## ADR-004: 옵션별 현재 재고 숫자와 변동 내역, 조건부 UPDATE로 차감

### Status
Accepted

### Context
판매, 판매 취소, 판매 수정, 입고, 입고 취소 때마다 재고가 바뀝니다. 관리자와 직원이 같은 옵션을 동시에 팔아도 재고가 0보다 작아지면 안 됩니다(NFR6). 재고 변동 내역 화면(FR3.6)이 있고, 상품 목록과 대시보드는 현재 재고와 재고 부족을 보여줍니다(FR2.4, FR3.5).

### Decision
Q2 A를 택합니다. `ProductOption`에 현재 재고(`currentStock`)를 두고, 재고가 바뀔 때마다 같은 트랜잭션에서 `StockMovement` 한 줄(구분, 변동량, 변동 후 재고, 관련 입고·판매, 처리자)을 남깁니다. 재고를 줄일 때는 `UPDATE ... SET current_stock = current_stock - ? WHERE id = ? AND current_stock >= ?`처럼 한 문장으로 하고, 바뀐 행이 0이면 재고 부족으로 보고 트랜잭션 전체를 되돌립니다. 판매에 품목이 여러 개면 옵션 id 순서로 차감해 서로 잠금을 기다리는 일을 줄입니다.

### Consequences
- 좋은 점: 동시 판매에서도 DB가 한 문장으로 판단하므로 음수 재고가 생기지 않습니다. 목록 화면은 숫자 하나만 읽어 빠릅니다.
- 나쁜 점: 현재 재고와 변동 내역 합계가 어긋날 가능성이 이론상 남습니다. 두 값을 늘 같은 트랜잭션에서 바꾸고, 테스트에서 "변동 내역의 마지막 변동 후 재고 = 현재 재고"를 확인합니다.
- 보안 영향: 재고를 바꾸는 기능은 `product`의 service만 갖고, 입고·입고 취소는 관리자 전용입니다.

### Alternatives Rejected
- Q2 B, 변동 내역 합계로 매번 계산하고 옵션 단위로 잠금: 어긋날 일은 없지만 목록과 대시보드가 매번 합계를 내야 해 느려지고, 잠금 처리(SELECT ... FOR UPDATE)가 H2와 MariaDB에서 다르게 동작할 수 있습니다.

## ADR-005: JWT는 HttpOnly·SameSite=Strict 쿠키, CSRF 토큰도 검사

### Status
Accepted

### Context
요구사항 8절에서 넘어온 질문입니다. 화면은 서버가 그리는 Thymeleaf라서 브라우저가 모든 요청(페이지 이동 포함)에 토큰을 자동으로 실어 보내야 합니다. 토큰은 JavaScript가 읽을 수 없어야 하고, 상태를 바꾸는 요청은 CSRF 공격을 막아야 합니다(NFR3). 앱은 `127.0.0.1`에서 http로만 열립니다(NFR1).

### Decision
Q3 A를 택합니다.
- JWT는 `HttpOnly`, `SameSite=Strict`, `Path=/` 쿠키에 담습니다. http로만 열리므로 `Secure`는 켜지 않습니다.
- Spring Security의 CSRF 보호를 켭니다. 서버에 세션을 두지 않으므로 CSRF 토큰은 쿠키 저장소(`CookieCsrfTokenRepository`)를 씁니다. Thymeleaf 폼(`th:action`)은 숨은 칸으로, `$.ajax`는 화면의 meta 태그에서 읽은 값을 `X-XSRF-TOKEN` 머리글로 보냅니다. 로그인 폼도 CSRF를 검사합니다.
- 상태를 바꾸는 요청은 GET으로 만들지 않습니다.

### Consequences
- 좋은 점: 방어가 두 겹입니다. SameSite가 다른 사이트에서 오는 요청을 막고, 그래도 빠져나간 경우(같은 사이트로 보는 다른 포트의 로컬 앱 등) CSRF 토큰이 막습니다. XSS가 생겨도 JWT 자체는 읽히지 않습니다.
- 나쁜 점: 모든 폼과 `$.ajax`에 CSRF 값을 넣어야 합니다. 공통 화면 틀과 공통 JavaScript 한 곳에서 처리합니다. CSRF 쿠키는 JavaScript가 읽을 수 있어야 하는 값이지만 인증 정보가 아니므로 괜찮습니다.
- 보안 영향: 이 결정 자체가 보안 결정입니다. 테스트에서 CSRF 토큰 없는 POST가 거부되는지, JWT 쿠키에 HttpOnly와 SameSite가 붙는지 확인합니다.

### Alternatives Rejected
- Q3 B, CSRF 토큰 없이 SameSite=Strict만: 코드가 줄지만, 같은 PC의 다른 포트에서 도는 앱은 브라우저가 같은 사이트로 보므로 SameSite만으로는 막지 못합니다.
- JWT를 localStorage에 두고 Authorization 머리글로 보냄: 서버 렌더링 페이지 이동에는 머리글을 붙일 수 없고, JavaScript가 토큰을 읽을 수 있어 NFR3에 어긋납니다.

## ADR-006: 마지막 활동 후 8시간 만료를 위해 토큰을 다시 발급

### Status
Accepted

### Context
요구사항 FR1.5는 "마지막 활동 후 8시간이 지나면 만료"입니다. JWT는 만든 뒤 내용(만료 시각)을 바꿀 수 없습니다.

### Decision
Q4 A를 택합니다. 토큰의 만료는 발급 후 8시간입니다. 인증된 요청이 올 때 토큰이 발급된 지 5분이 지났으면 새 토큰(만료 8시간)을 발급해 같은 쿠키를 바꿉니다. 그래서 실제 만료는 마지막 활동 후 8시간(최대 5분 차이)입니다. 만료되었거나 서명이 틀린 토큰으로 온 요청은 로그인 화면으로 보내고 "로그인 시간이 지나 다시 로그인해 주세요."를 보여준 뒤, 로그인하면 원래 화면으로 돌아갑니다. 로그아웃은 쿠키를 지웁니다.

### Consequences
- 좋은 점: 요구사항을 바꾸지 않습니다. 화면을 쓰는 동안에는 로그인이 끊기지 않습니다.
- 나쁜 점: 5분마다 쿠키가 바뀝니다. 서버에 토큰 목록을 두지 않으므로 로그아웃 전에 복사된 토큰은 만료까지 유효합니다. 이 앱은 `127.0.0.1` 전용이고 쿠키가 HttpOnly라 받아들일 수 있는 위험으로 봅니다. 계정 사용 중지는 ADR-002의 계정 확인으로 바로 막힙니다.
- 보안 영향: 서명 키는 환경변수로 받고 로그에 쓰지 않습니다. 토큰에는 사용자 id와 역할만 넣고 비밀번호나 개인 정보는 넣지 않습니다.

### Alternatives Rejected
- Q4 B, 로그인 후 8시간 고정: 코드가 단순하지만 일하는 중에 로그인이 끊기고, 요구사항 FR1.5를 바꿔야 합니다.
- 짧은 접근 토큰 + 갱신 토큰: 이 규모의 로컬 앱에는 과하고, 갱신 토큰 저장소가 필요합니다.

## ADR-007: 직원 요청과 변경 이력은 JSON 글로 저장

### Status
Accepted

### Context
직원의 수정 요청은 바꿀 판매 내용 전체(품목, 수량, 할인, 결제 수단, 거래처, 일시, 메모, 개월 수)를 담고, 관리자가 승인할 때 반영됩니다(FR6.3, FR6.4). 변경 이력은 누가, 언제, 무엇을 바꿨는지 바꾸기 전 값과 바꾼 뒤 값을 남기고 지울 수 없습니다(FR6.2). 화면 설계 검토 의견 R-06에 따라 승인할 때는 그 시점의 재고와 입금 상태로 다시 계산합니다.

### Decision
Q7 A를 택합니다. `ChangeRequest.payloadJson`에 바꾼 뒤의 판매 내용을, `SaleHistory.beforeJson`과 `afterJson`에 바꾸기 전과 뒤의 판매 내용(품목, 할인, 금액, 회차 포함)을 JSON 글 한 칸으로 저장합니다. 칸의 종류는 H2와 MariaDB 모두에 있는 긴 글(CLOB/TEXT)이고 DB의 JSON 기능은 쓰지 않습니다(NFR9). 비교 화면(S15)과 승인은 그때마다 현재 판매와 요청 내용을 비교해 다시 계산합니다. 이력 테이블에는 수정·삭제 기능을 만들지 않습니다.

### Consequences
- 좋은 점: 테이블이 두 개로 끝나고, 판매 모양이 바뀌어도 테이블을 고칠 필요가 적습니다. 승인할 때 지금 상태로 다시 계산하므로 요청 뒤에 재고나 입금이 바뀌어도 잘못 반영되지 않습니다.
- 나쁜 점: 이력 안의 값으로 검색하거나 집계할 수 없습니다. 이 앱은 이력을 판매 상세에서 보여주기만 하므로 괜찮습니다. JSON 모양에 판 번호(schemaVersion)를 넣어 나중에 모양이 바뀌어도 옛 이력을 읽을 수 있게 합니다.
- 보안 영향: JSON에는 판매 정보만 넣고 비밀번호·토큰은 넣지 않습니다. 화면에 보여줄 때는 Thymeleaf가 글자를 이스케이프합니다.

### Alternatives Rejected
- Q7 B, 요청 품목·이력 품목을 판매와 같은 모양의 별도 테이블로 저장: SQL로 비교할 수 있지만 테이블이 네 개 이상 늘고, 판매 모양이 바뀔 때마다 함께 고쳐야 합니다.

## ADR-008: 할부 규칙: 0원 회차 처리와 첫 예정일

### Status
Accepted

### Context
화면 설계 승인 때 남겨 둔 검토 의견 R-01, R-04, R-05입니다. 할부 판매의 금액을 고치면 (새 판매 금액 - 입금 합계)를 미입금 회차에 똑같이 나누는데, 남은 금액이 0원이거나 미입금 회차 수보다 작으면 0원 회차가 생깁니다. 첫 예정일을 어떤 날짜까지 받을지, 판매를 고칠 때 예정일을 어떻게 할지도 정해져 있지 않았습니다. 지난 날짜 판매도 등록할 수 있습니다(FR5.2).

### Decision
Q5 A와 Q6 A를 택합니다.
- 금액 수정 후 남은 금액(새 판매 금액 - 입금 합계)이
  - 0보다 작으면 거부: "입금된 금액보다 작게 바꿀 수 없습니다. 입금을 먼저 취소하세요."
  - 0이면 미입금 회차를 모두 없애고 판매를 완납으로 봅니다.
  - 0보다 크지만 미입금 회차 수보다 작으면 거부: "남은 금액이 너무 작아 회차를 나눌 수 없습니다."
  - 미입금 회차가 없는데 금액이 바뀌면 거부: "입금되지 않은 회차가 없어 금액을 바꿀 수 없습니다."(화면 설계 1절)
- 첫 예정일은 판매일(Asia/Seoul 날짜)과 같거나 뒤인 날짜만 받습니다. 기본값은 판매일의 다음 달 같은 날입니다. 지난 판매를 나중에 입력하면 첫 예정일도 지난 날짜일 수 있고, 그러면 바로 연체로 보입니다.
- 판매를 고칠 때 첫 예정일은 입금 기록이 없을 때만 바꿀 수 있고, 판매 일시를 바꿔도 예정일은 자동으로 바뀌지 않습니다. 고친 판매일이 첫 예정일보다 뒤가 되면 "첫 예정일은 판매일보다 앞설 수 없습니다"로 거부합니다.
- 개월 수는 1~36이고, 입금 기록이 없을 때 개월 수를 바꾸면 회차 전체를 다시 나눕니다.

### Consequences
- 좋은 점: "판매는 완납인데 회차는 미입금"처럼 화면이 어긋나는 경우가 없어집니다. 지난 판매도 실제 일정대로 입력할 수 있습니다.
- 나쁜 점: 남은 금액이 0원이 되어 회차를 없애면 판매의 `installmentMonths`와 실제 회차 수가 달라집니다. 화면은 실제 회차만 보여주고, 이력에 없앤 회차를 남깁니다.
- 보안 영향: 없음. 규칙은 서버 service에서 검사하고 화면은 같은 규칙으로 미리 알려 주기만 합니다.

### Alternatives Rejected
- Q5 B, 0원 회차가 생기는 수정은 남은 금액 0원도 포함해 모두 거부: 단순하지만 마지막 입금 뒤 금액을 입금 합계와 같게 맞추는 정당한 수정을 막습니다.
- Q5 C, 0원 회차를 "입금 완료(0원)"로 자동 처리: 실제로 받지 않은 입금 기록이 생겨 입금 이력이 사실과 달라집니다.
- Q6 B, 첫 예정일은 오늘 이후만: 지난 판매를 나중에 입력할 때 실제 일정을 넣을 수 없습니다.
- Q6 C, 첫 예정일을 입력받지 않고 늘 다음 달 같은 날: 거래처와 다른 날짜로 약속한 경우를 기록할 수 없고, 화면 설계(S12의 첫 예정일 칸)와 다릅니다.

## ADR-009: Spring Boot 버전은 Java 25 공식 지원 최신 안정판

### Status
Accepted

### Context
요구사항 8절에서 넘어온 질문입니다. README는 Java 25와 "Spring Boot LTS"를 정했습니다. Spring Boot는 따로 LTS 판을 내지 않으므로, 어떤 기준으로 고를지 정해야 했습니다. 정확한 버전 번호는 실제로 받을 수 있는 버전을 확인해야 해서 Code Generation에서 정합니다.

### Decision
Q8 A를 택합니다. Java 25를 공식 지원하는 가장 최신 안정판(GA) Spring Boot를 쓰고, MyBatis Spring Boot Starter, Gradle, JWT 라이브러리, Bootstrap WebJar도 그 버전과 맞는 최신 안정판을 씁니다. Code Generation 계획에서 버전 번호와 확인한 근거를 적고, 뼈대 단계에서 `./gradlew build`가 Java 25로 통과하는지 확인합니다.

### Consequences
- 좋은 점: 공식 지원 범위 안에 있어 빌드·테스트 문제가 적고 보안 패치를 오래 받습니다.
- 나쁜 점: 최신 판은 인터넷 자료가 적을 수 있습니다. 문제가 생기면 Code Generation에서 사용자에게 묻습니다.
- 보안 영향: 최신 안정판이라 알려진 취약점 패치가 반영되어 있습니다.

### Alternatives Rejected
- Q8 B, Spring Boot 3.x 마지막 판: 자료는 많지만 Java 25 공식 지원이 보장되지 않아 빌드가 실패할 위험이 있습니다.

## ADR-010: 판매 중복 저장과 동시 수정 막기

### Status
Accepted

### Context
저장 버튼을 두 번 눌러도 판매는 한 건만 만들어야 합니다(FR5.6). 관리자가 판매를 고치는 동안 다른 관리자 화면이나 승인이 같은 판매를 바꿀 수 있습니다(FR6.1, FR6.4). 재고 동시성은 ADR-004가 맡습니다.

### Decision
- 판매 등록 화면은 열릴 때 임의의 요청 토큰을 만들어 폼에 넣고, 서버는 이를 `Sale.requestToken`(유일 값)에 저장합니다. 같은 토큰으로 다시 오면 새로 만들지 않고 이미 만든 판매로 보냅니다.
- `Sale.version`을 두고, 수정·취소·입금·입금 취소·승인은 화면이 읽은 version과 같을 때만 반영합니다(`WHERE id = ? AND version = ?`). 다르면 "다른 사용자가 먼저 바꿨습니다. 화면을 새로 열어 주세요."로 거부합니다.

### Consequences
- 좋은 점: 버튼 두 번 클릭, 브라우저 다시 보내기에도 판매가 한 건만 생깁니다. 두 사람이 같은 판매를 고쳐도 한쪽 변경이 조용히 사라지지 않습니다.
- 나쁜 점: 폼과 버튼 요청에 version 값을 실어 보내야 합니다.
- 보안 영향: 요청 토큰은 인증 정보가 아니고 중복 방지에만 씁니다.

### Alternatives Rejected
- 화면에서 버튼만 끄기: 화면 설계 S12-2가 버튼을 끄지만, 서버가 막지 않으면 다시 보내기나 느린 네트워크에서 두 건이 생길 수 있습니다.
- 판매 단위 비관적 잠금(SELECT ... FOR UPDATE): H2와 MariaDB의 동작 차이가 있고, 화면을 연 채로 두면 잠금을 오래 잡을 수 있습니다.
