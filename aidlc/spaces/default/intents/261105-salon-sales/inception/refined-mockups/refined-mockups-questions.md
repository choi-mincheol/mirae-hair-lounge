## Q1. [디자이너] 메뉴 위치와 화면 틀

A. 왼쪽 세로 메뉴(항상 보임) + 오른쪽 본문. 위쪽 줄에는 로그인한 사용자 이름, 비밀번호 변경, 로그아웃
B. 위쪽 가로 메뉴 + 아래 본문. 메뉴가 많으면 "더보기"로 묶음
C. 위쪽 가로 메뉴에 큰 분류(판매 / 상품·재고 / 거래처 / 관리)만 두고, 누르면 하위 메뉴가 펼쳐짐

## Q3. [디자이너] 접근성 수준

요구사항에서 "재고 부족", "연체"를 색만이 아니라 글자로도 표시하기로 했습니다(FR3.5, FR7.6). 그 밖에 어디까지 맞출지 정합니다.

A. WCAG 2.1 AA 수준: 키보드만으로 모든 기능 사용, 포커스 표시, 글자 대비 4.5:1 이상, 모든 입력 칸에 라벨, 오류는 글자로 안내
B. 기본만: 입력 칸 라벨과 글자 오류 안내, 색만으로 상태를 표시하지 않기. 키보드·대비 기준은 따로 맞추지 않음
X. Other (please specify)

[Answer]: B

## Q4. [디자이너] 판매 등록에서 품목을 고르는 방법

판매 한 건에 여러 옵션(예: OO 염색약 7N)을 담습니다(FR5.1). 가장 자주 쓰는 화면이라 입력 방법이 속도를 좌우합니다.

A. 검색창 하나: 상품명·브랜드·바코드를 입력하면 "상품 - 옵션 (재고 n)" 후보가 아래에 뜨고, 고르면 품목 표에 한 줄이 추가됨(수량 1, 표에서 수정)
B. "품목 추가" 버튼을 누르면 상품 목록 창(모달)이 열리고, 분류·검색으로 찾아 여러 옵션을 체크한 뒤 한 번에 추가
C. 분류 → 상품 → 옵션 순서로 드롭다운 세 개를 골라 추가
D. A와 B 모두(빠른 입력은 검색창, 찾아보기는 목록 창)
X. Other (please specify)

[Answer]: B

## Q5. [디자이너] 판매 등록 화면 구성

판매 등록에는 품목, 거래처, 판매 일시, 결제 수단, 할인, 외상·할부 회차가 들어갑니다(FR5, FR7.1).

A. 한 화면: 위에 거래처·일시·결제 수단, 가운데 품목 표, 아래에 할인과 합계. 결제 수단을 "외상·할부"로 바꾸면 할부 회차 입력 칸이 그 자리에서 펼쳐짐. 저장 버튼 한 번으로 저장
B. A와 같지만, 저장을 누르면 품목·금액·할부 일정을 요약한 확인창을 한 번 더 보여주고 "확인"을 눌러야 저장
C. 단계형: 1) 품목 → 2) 거래처·결제·할인 → 3) 할부 회차(외상·할부일 때) → 4) 요약 확인 후 저장
X. Other (please specify)

[Answer]: B

## Q6. [디자이너] 직원의 수정·취소 요청과 관리자 승인 화면

직원은 판매 수정·취소를 요청하고 관리자가 승인해야 반영됩니다(FR6.3, FR6.4). 요청과 승인을 어디서 하는지 정합니다.

A. 직원: 판매 상세의 "수정 요청" 버튼은 판매 수정 화면과 같은 모양의 입력 화면을 열고, "취소 요청"은 사유를 적는 확인창을 엶. 관리자: "승인 요청" 메뉴의 대기 목록에서 한 건을 열면 바뀌기 전과 바뀐 뒤를 나란히 비교해 보고 승인 또는 거절(사유 입력)
B. A와 같지만, 관리자는 대기 목록에서 바로 승인·거절만 하고, 바뀌는 내용은 목록의 한 줄 요약으로만 봄
C. 요청과 승인을 모두 판매 상세 화면 안에서 처리(별도 승인 메뉴 없이, 대시보드의 "승인 대기" 숫자를 누르면 해당 판매 목록으로 이동)
X. Other (please specify)

[Answer]: A

## Q7. [제품 관리자] 외상·할부 판매의 금액을 고칠 때 회차 처리

요구사항에서 남겨 둔 질문입니다: 할부 회차가 있는 판매의 품목이나 할인을 고쳐 판매 금액이 바뀌면, 회차 합계가 판매 금액과 맞지 않게 됩니다(FR7.1은 합계가 같아야 저장).

A. 아직 입금되지 않은 회차들에 바뀐 차액을 자동으로 다시 나눠 채우고(끝전은 마지막 회차), 사용자가 저장 전에 고칠 수 있음
B. 자동으로 고치지 않음. 수정 화면에 "할부 합계가 판매 금액과 다릅니다"를 보여주고, 사용자가 회차를 직접 맞춰야 저장됨
C. 입금 기록이 하나라도 있으면 금액에 영향을 주는 수정(품목·수량·할인)을 막음. 입금이 없으면 회차 전체를 처음처럼 다시 나눠 채움
X. Other (please specify)

[Answer]: X. 할부금 중 입금금액은 입력하여 남은금액 등이 나올 수 있도록

## Q8. [개발자] 화면 스타일 도구

화면 모양(버튼, 표, 입력 칸, 확인창)을 무엇으로 만들지 정합니다. 작업 방식에서 npm 같은 프런트엔드 빌드 도구는 쓰지 않기로 했습니다.

A. Bootstrap 5를 Gradle 의존성(WebJars)으로 받아 앱에 포함. 인터넷 없이도 화면이 그대로 나옴
B. Bootstrap 5를 CDN 주소로 불러옴. 설정은 가장 간단하지만, 인터넷이 끊기면 화면 모양이 깨짐
C. 외부 라이브러리 없이 직접 만든 CSS 파일 하나로 필요한 모양만 만듦

## Q9. [제품 관리자] 할부 판매 금액을 고칠 때 남은 금액 처리

Q7에서 "할부금 중 입금금액은 입력하여 남은금액 등이 나올 수 있도록"이라고 하셨습니다. 그래서 할부 일정에는 회차마다 예정 금액, 입금된 금액, 남은 금액을 보여주고, 판매 위에는 판매 금액, 입금 합계, 남은 금액을 보여주겠습니다(입금은 앞 회차부터 채움, FR7.5). 판매 금액이 바뀌었을 때 회차를 어떻게 맞출지는 아직 정해지지 않아 여쭙니다.

A. 남은 금액(바뀐 판매 금액 − 입금 합계)을 아직 다 입금되지 않은 회차에 자동으로 다시 나눠 채움(끝전은 마지막 회차). 사용자가 저장 전에 회차를 고칠 수 있음
B. 회차는 자동으로 바꾸지 않음. 남은 금액과 회차 합계의 차이를 보여주고, 사용자가 회차를 직접 맞춰야 저장됨
C. 입금이 끝난 회차는 그대로 두고, 남은 금액을 몇 회로 나눌지(회차 수와 다음 예정일)를 다시 입력하면 새로 나눠 채움
X. Other (please specify)

[Answer]: X. 판매금액을 할부개월 수에 맞춰 자동으로 나눠놓고, 입금확정은 각 로우에서 그냥 버튼으로 입금 을 눌러 처리되었음을 나타나게 한다. 프로토타입이므로 금액을 별도 수정하기보단 버튼으로 입금확인처리 등의 작업으로 진행하면 된다

## Q10. [제품 관리자] 승인된 요구사항과 달라지는 부분 확인

Q9 답대로 하면 승인된 요구사항의 몇 가지가 바뀝니다. 지금 요구사항에는 입금할 때 금액을 직접 입력하고 여러 번 나눠 입금할 수 있게(FR7.2), 회차의 예정일과 금액을 직접 고칠 수 있게(FR7.1, FR7.7) 되어 있습니다. 어떻게 맞출지 정해 주세요. 정한 내용은 화면 설계 문서에 "요구사항과 달라진 점"으로 적어, 다음 단계(Domain Design)가 그대로 따르게 합니다.

A. Q9 답으로 바꾼다. 회차는 개월 수로 자동으로 똑같이 나누고(끝전은 마지막 회차) 금액과 예정일은 고치지 않는다. 각 회차 줄의 "입금" 버튼을 누르면 그 회차 전액이 오늘 날짜로 입금 처리된다. 잘못 눌렀을 때를 위해 관리자에게 "입금 취소" 버튼을 둔다. 판매 금액이 바뀌면 입금되지 않은 회차들에 남은 금액을 다시 똑같이 나눈다
B. A와 같지만 "입금 취소" 버튼은 두지 않는다
C. A와 같지만 회차 예정일은 고칠 수 있게 남겨 둔다
X. Other (please specify)

[Answer]: A
